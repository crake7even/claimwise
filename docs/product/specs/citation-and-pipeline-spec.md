# Citation & Pipeline Spec

> 编写：2026-11-27。读者是执行优化的 Agent。文中行号对应编写时的工作区，动手前以实际代码为准。

## 1. 目标

ClaimWise 的卖点是“回答可追溯”。现在检索和生成本身是可靠的（见 README 评测结果），但引用这条链路从后端数据到前端展示都有缺口：用户看不出哪些资料真的支撑了回答，来源数据带着内部实现的痕迹，多轮对话还可能标错编号。本轮把这条链路做完整，并让检索过程对用户可见。

## 2. 范围与约束

**做**：来源数据契约、引用正确性、来源展示、过程可见性四组，共 15 项（第 4 节）。

**不做**：
- 不改切分、chunk 的 `content`、chunk id、检索参数、融合与 Rerank 逻辑、`SYSTEM_PROMPT`。
- 不做“句子级高亮”（靠文本匹配猜哪句支撑回答，猜错会误导保险结论）。
- 不展示相关度分数，不处理 Render 冷启动，不新增任何外部服务、密钥或环境变量。
- 不换视觉风格：沿用现有 brand 色、圆角、阴影和 `index.css` 里的类。

**工作方式**：
- 从 `master` 建分支 `feat/citation-ux`。工作区有 2026-10-26 的未提交改动（`frontend/src/api.ts`、`frontend/src/components/ChatMessage.tsx`、`frontend/src/sourcePresentation.ts`、`docs/product/testing.md`），是本轮的半成品，带到分支上继续做，不要丢弃。`backend/eval/reports/judge-*.json` 三个未跟踪文件不属于本轮，不要动。
- 不推送 `master`，不部署，不执行 `scripts/index_es.py`。
- 本机有提交格式 hook，可能拦截不带工单号的提交。被拦时不要绕过，把“暂存、提交、推送分支”写成一条命令交给用户执行。
- 删除任何文件前列出清单请用户确认。
- 密钥只从 `backend/.env` 读取，不打印、不写入代码或日志。

## 3. 已确认的现状

线上用示例问题“员工喝酒开车出事，意外险赔吗？”（语义理解模式）实测：回答引用了 [1]、[2]、[4]，下方并列 6 个来源胶囊。

- 1 和 4、2 和 3、5 和 6 各来自同一份文档，胶囊标题被截断后看起来一样。
- 没被引用的 3、5、6 与被引用的没有区别。
- 5、6 的标题是“3-平安企业团体综合意外险”，带文件编号；条款名显示为“三、”。
- 展开后正文第一行是“《平安企业团体综合意外险》三、”，重复了标题。
- 点正文角标，内容展开在页面最下方，被输入框挡住一部分。
- 输入框的模式选择器停在“快速检索”，而这条回答用的是“语义理解”。

## 4. 条目

每项格式：问题 → 想要的效果 → 验收标准。

### A. 来源数据契约（后端）

**A1 标题带文件编号**
- 问题：`build_sources`（`backend/api_server.py:153`）用 `file_name` 去扩展名作标题，保留了“3-”；而 `document_loader.doc_title()` 已有去前缀规则，两处不一致。
- 效果：对外的本地来源标题不含文件编号。
- 验收：`sources` 事件和 `/api/search` 返回中，所有 `kind=local` 的 `title` 不匹配 `^\d+-`；有单测。

**A2 摘录带检索前缀行**
- 问题：chunk 的 `content` 首行是为检索写入的“《文档名》条款名”（`document_loader.py:161-162`），原样作为 `snippet` 下发。
- 效果：对外 `snippet` 只有条款正文。
- 验收：本地来源的 `snippet` 首行不等于“《title》section”；有单测。

**A3 条款名无意义**
- 问题：非条款类文档的 `section` 只是序号（“三、”），问答类被截到 24 字（`document_loader.py:121-125`）。
- 效果：对外 `section` 是人能读懂的小节名：只有序号或为空时，取正文第一行（超过 30 字截断加省略号）；问答类给完整问句。
- 验收：遍历全部 chunk 生成的对外 `section`，没有只含序号和标点的值；有单测覆盖条款类、序号类、问答类、空标签四种。

**A4 以上三项只改对外输出**
- 约束：`DocChunk.content`、chunk id、送进模型的上下文都不变。
- 验收：`backend/workspace/embedding_cache.json` 无 diff；`build_context_block` 对同一检索结果的输出与改动前逐字相同（加一条固定样例的单测）；`eval/validate_dataset.py` 通过；离线 `eval/run_eval.py` 的 Hit@1、Recall、MRR 与改动前数值相同。README 的接口说明补上字段含义。

### B. 引用正确性

**B1 多轮对话里旧编号污染新回答**
- 问题：前端 `buildHistory`（`frontend/src/App.tsx:39-47`）把含 `[1]`、`[2]` 的旧回答原样发回，后端直接拼进对话（`api_server.py:245-246`），查询改写也会读到（`query_rewriter.py:32-35`）。旧编号指向上一轮的资料，本轮资料重新从 1 编号，模型可能沿用旧编号。这是从代码推断的风险，未复现。
- 效果：进入模型和改写器的历史回答不含引用标记；会话里显示和导出的原文不变。
- 验收：先在 `eval/smoke.py` 加一个两轮追问场景并确认它能暴露问题或至少覆盖该路径；修复后，第二轮回答里每个编号都在本轮 `sources` 范围内。加单测：给定含引用标记的历史，送进模型的 messages 里不含 `[n]`。

**B2 引用格式容错**
- 问题：`linkCitations`（`ChatMessage.tsx:23-28`）只识别 `[n]`。模型写成 `[1、2]`、`[1,2]`、`[1-3]`、`【1】` 时不会变成角标。
- 效果：这些写法都渲染成对应的多个角标；编号不在本轮来源里的保持原样文本、不可点击；流式过程中半截的 `[1` 不闪烁成错误角标。
- 验收：解析逻辑是纯函数，单测覆盖上述每种写法、越界编号、Markdown 链接 `[文字](url)` 不被误伤。

**B3 被引用集合**
- 效果：前端从正文解析出“被引用的编号集合”，随流式输出更新，供 C 组使用。
- 验收：同 B2 的单测覆盖；历史会话重新打开后结果一致。

### C. 来源展示（前端）

**C1 按文档合并**
- 效果：同一文档只出现一个胶囊，显示去编号的文档名和条款数量；悬停显示完整文档名。展开后组内逐条列出“编号 + 条款名 + 正文”。
- 验收：上面的实测问题只出现 3 个文档胶囊。

**C2 区分“引用”与“未引用”**
- 效果：标题为“引用资料 · N”，只含被引用的文档；其余收进默认折叠的“其他检索结果 · M”。回答没有任何引用（拒答、降级摘要）时，不出现“引用资料”字样，全部列为“检索结果”。
- 验收：实测问题默认只看到被引用的 2 份文档；展开“其他检索结果”能看到剩下的 1 份；联网来源保留地球图标和“打开原文”。

**C3 点角标就地查看**
- 效果：桌面端点正文角标，在角标旁弹出卡片：文档名、条款名、正文（超长可滚动）。Esc、点外部、再点角标都能关闭；键盘 Tab 可到达角标并用 Enter 打开。宽度不超过 640px 时改为底部抽屉。项目已依赖 `@base-ui/react`，优先用它的 Popover / Dialog，不新增 UI 库。
- 验收：1440×900 下点角标，卡片完整落在视口内，不被输入框遮挡；375×812 下为底部抽屉，可滚动、可关闭。

**C4 底部展开不被遮挡**
- 效果：在底部列表点胶囊展开后，展开面板自动滚进可视区域。
- 验收：对话区滚到底时点最后一条回答的胶囊，面板完整可见。

**C5 旧数据兼容**
- 问题：浏览器 localStorage 和用户导出的 JSON 里是旧格式来源（带编号前缀、带前缀行）。
- 效果：前端展示层保留对旧格式的清洗（`sourcePresentation.ts` 现有逻辑），新旧数据显示一致。
- 验收：导入一份改动前导出的会话文件，来源显示与新回答一致，无编号前缀、无重复标题行。

### D. 过程可见性

**D1 检索阶段提示**
- 问题：从发送到出字之间只有“正在检索资料…”，查询改写、召回、重排、生成四步对用户不可见。
- 效果：后端在流里增加 `stage` 事件（改写 / 召回 / 重排 / 生成），前端加载提示按阶段更新文案。旧前端会忽略未知事件类型（`api.ts` 的 `handleLine`），协议向后兼容。
- 验收：`tests/test_rag.py` 的流式协议用例更新并通过，事件顺序为 `stage* → sources → stage → delta* → done`；浏览器里能依次看到阶段文案；冷启动提示（8 秒后的“服务可能正在唤醒”）不受影响。

**D2 展示改写后的检索用语**
- 问题：`sources` 事件已带 `rewritten`，前端没有使用。
- 效果：改写结果与原问题不同时，在来源区显示一行“检索用语：……”。
- 验收：实测问题能看到改写后的用语（如含“酒后驾车”）；快速检索首轮不改写时不显示这一行；旧会话没有该字段时不报错。

**D3 模式选择器与实际模式不一致**
- 问题：点示例问题按它自带的模式发送，输入框选择器不跟着变（见第 3 节）。
- 效果：发送后选择器同步为本次使用的模式。
- 验收：点“语义理解”示例后，选择器停在“语义理解”，接着直接输入追问仍走语义理解。
