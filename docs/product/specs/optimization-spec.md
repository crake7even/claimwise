# Optimization Spec

## 1. 版本目标

修复现有 Demo 中影响可信度和可用性的问题，并把检索层整理成可独立复用的服务，为后续接入外部 Agent（如 off-platform distribution 向导）做准备。

本轮不换技术栈、不引入数据库和账号体系，不处理线上部署流程。

## 2. 分阶段计划

按优先级拆成 4 个阶段，每个条目对应一个功能分支和一个 PR，可单独验证和回滚。

### E：评测集与评测流水线（先于检索改动建立基线）

目的：每次改检索或生成逻辑，都能用数据说明效果变好还是变差，而不是靠肉眼判断。

**数据集** `backend/eval/dataset.jsonl`，每行一个样本：

```json
{"id": "emp-001", "question": "雇主责任险的赔偿限额怎么规定？", "category": "fact",
 "expected_sources": [{"file": "2-雇主责任险", "keywords": ["赔偿限额"]}],
 "key_points": ["每人伤亡赔偿限额", "累计赔偿限额"], "should_refuse": false}
```

- 用 `file` 加关键词定位依据片段，而不是 `chunk_id`，这样换切分策略后标注仍然有效。
- 规模约 80 到 100 条，覆盖全部 13 份文档。题型分布如下：

| category | 说明 | 占比 |
|---|---|---|
| fact | 单文档事实查询（保障范围、免责、限额、等待期） | 40% |
| paraphrase | 口语化或同义改写提问，主要考察语义召回 | 20% |
| compare | 跨文档对比 | 15% |
| procedure | 理赔流程、材料等多段落问题 | 10% |
| out_of_scope | 知识库里没有答案，期望模型拒答或说明资料不足 | 15% |

- 生成方式：用 LLM 按文档批量起草候选问题，再人工逐条审核关键点和依据。审核环节必须保留。
- 留出约 20% 作为 holdout，不参与调参。

**指标**

| 层 | 指标 | 计算方式 |
|---|---|---|
| 检索 | Hit@1 / Recall@5 / MRR | 命中 `expected_sources` 的文件名和关键词即算命中，纯离线，CI 可以跑 |
| 生成 | 关键点覆盖率 | `key_points` 在回答中被覆盖的比例，用 LLM-judge 判定 |
| 生成 | 忠实度 | 回答中的结论能否由召回片段支撑，用 LLM-judge 判定 |
| 生成 | 拒答准确率 | `out_of_scope` 题正确拒答、正常题不误拒的比例 |
| 性能 | 首字延迟 / 总延迟 | 按 P50 和 P95 统计 |

**工具** `backend/eval/run_eval.py`

- `--mode quick|semantic|web` 和 `--stage retrieval|full`：检索评测不需要 API Key；完整评测需要 DashScope。
- 输出 `eval/reports/<日期>-<分支>.md`，内容包括各题型分项得分和失败样本，并支持和基线报告 diff。
- CI 只跑离线的检索评测，设最低阈值，指标退化时 CI 失败。

### U：升级优化（以评测结果驱动取舍）

| # | 升级项 | 说明 | 预期主要提升的指标 |
|---|---|---|---|
| U1 | Rerank | 召回 top 20 后用 DashScope `gte-rerank` 重排，取 top 5 | Hit@1、忠实度 |
| U2 | 查询改写 | 多轮场景下把追问改写成独立问题；口语化表达改写成条款用语 | paraphrase 题 Recall |
| U3 | 父子块 | 用小块检索、返回所属条款大块给 LLM | 关键点覆盖率 |
| U4 | 低置信拒答 | 最高分低于阈值时直接说明资料不足，不让 LLM 硬答 | 拒答准确率 |
| U5 | 引用对齐 | 要求回答逐条标注 `[1][2]`，前端可点击查看原文片段 | 忠实度、可信度 |
| U6 | 可观测性 | 每次请求记录召回结果、耗时、所用模式（不记录用户原文以外的敏感信息） | 定位失败原因 |

每个升级项单独开分支，PR 描述里附上评测报告前后对比；指标没有提升的升级项不合入。

## 3. 不做什么

- 不接入公司系统或公司语料（集成推迟，见个人项目约定）。
- 不引入向量数据库；chunk 数量在千级以内时，内存暴力检索足够。
- 不做账号、服务端会话、限流（README 已标注为已知限制）。
- 本轮不处理部署流程。

## 4. 通用验收

- 后端：`python -m unittest discover -s tests -v` 全部通过，新增逻辑有对应单测。
- 前端：`npm run lint && npm run build` 通过；UI 改动经浏览器实测，桌面和 375px 宽度各验证一次。
- 每个 PR 只包含对应条目的改动。

## 5. 建议执行顺序

`0.1 → E（数据集 + 检索评测，跑出基线）→ 0.2（文档加载）→ 0.3(+1.6) → 0.4 → 1.2 → 1.1/U5 → U1 → 1.4/U3 → 1.3(+1.5)/U2 → U4 → 2.x → U6 → P3`

评测集必须在去重、RRF 这些检索改动之前完成，否则没有基线可以对比。0.1 是纯前端改动，不受影响，可以先做。
